Review Pass 4: Security and Data Integrity
Map data from browser inputs through edge functions, database, reviewer access, notification provider, backups, logs, analytics, and any model/CRM integrations. Identify trust boundaries and which fields are client-authored versus server-authoritative.
Inspect and safely test:
Access & authorization: Anonymous access, authenticated-but-unapproved access, reviewer permissions, cross-account access, direct REST/RPC access, case-reference enumeration, and forwarded notification links. Report broad reviewer access as a finding only against the intended authorization model, not an invented per-reviewer ownership requirement.
Database security: RLS, table/schema grants, policies on every sensitive table, reviewer provisioning/self-enrollment, service-role bypass, SECURITY DEFINER functions, safe search paths, actor attribution, RPC input validation, correction access, and write permissions.
Immutability & corrections: Database immutability and append-only corrections through every accessible path. Check how correction overlays affect summaries while retaining original answers. Separate appropriate retention/deletion mechanisms from unauthorized snapshot editing.
Server-side snapshot validation: Server validation of questionnaire versions, known question/field IDs, source metadata, timeframes, held/approved status, source-versus-supplemental classification, dispositions, complete question inventory, branch applicability, review confirmation, flags, crisis state, and chronology. Test whether a syntactically valid but fabricated client snapshot can be accepted as authoritative.
Payload & resource bounds: Input types/lengths/counts, nested array caps, invalid dates, empty answer arrays, malformed JSON, oversized/chunked/multibyte bodies, and body-read resource usage. Verify byte limits are actually bytes, not only JavaScript character counts.
Abuse & origin controls: Abuse protections, durable versus per-instance limits, client-IP trust, anonymous submission spam, request timeouts, and rate-limit evasion. Distinguish CORS from caller authentication; do not treat a spoofable Origin as proof of a trusted client.
Injection & rendering: React rendering, raw HTML/Markdown, links, exports, log injection, SQL/RPC construction, and any downstream interpretation of untrusted text. Demonstrate a sink and exploit path before labeling a harmless string as executable XSS/SQL injection.
Secrets exposure: Service-role/provider secrets in source, git history available to the audit, browser bundles, VITE_* variables, source maps, CI artifacts, logs, and public config. Distinguish intentionally public Supabase publishable/anon keys from secret service-role credentials.
Session & auth storage: Auth session storage, reviewer token exposure, MFA enrollment versus actual enforcement, logout/session expiry, cache behavior, and privileged-session protections. Distinguish persisted auth tokens from persisted health answers.
Sensitive data leakage: Health information in URLs, browser persistence, analytics, session replay, error traces, console logs, provider metadata, email content, exported files, and public links (see HHS FAQ on emailing ePHI). Evaluate deployment headers/CSP/cache rules only where evidence is available.
Operational & lifecycle controls: Retention/deletion jobs, backup retention, access/audit logs, incident response, vendor arrangements, and whether controls exist in code, configuration, approved procedure, or documentation only.
Treat suspected weaknesses as hypotheses until the relevant path is traced. A feature flag or a client-side disabled button is not a server security control. Conversely, a public intake endpoint is not automatically a vulnerability if its intended public behavior is bounded appropriately.

Evidence and Finding Standards
For each finding provide:
Stable ID & title: Clear ID, title, affected workflow/control, and concise description.
Severity: Critical, High, Medium, Low, or Informational; explain impact, exposure, and prerequisites. Avoid arbitrary numeric scoring.
Classification: confirmed defect, documented limitation, suspected issue, operational evidence missing, legal/counsel decision, or future-feature pre-enable gate.
Verification status: runtime reproduced, statically demonstrated, documentation-only, or not verified. Static proof can establish a defect; do not claim execution that did not occur.
Code & config evidence: Commit-pinned file links with line ranges, relevant database objects/configuration, and minimal redacted excerpts.
Reproduction details: Safe reproduction steps or test fixture, expected versus observed behavior, and whether the scenario is preview, local, staging, or production.
Concrete consequence: Impact for a customer, reviewer, evidence record, or operation.
Remediation & regression test: Smallest suitable remediation, proposed owner/dependency, and a regression test proving closure.
Launch impact: Whether it blocks launch now, blocks only a feature/configuration, or is nonblocking—and why.
A documented limitation can still block launch. An intentional absence of carrier quoting is not a defect when it is out of scope. An unavailable live environment is a verification gap, not proof the system is either safe or broken. Identify root causes and consolidate duplicates while retaining distinct consequences/tests. Record meaningful negative findings only when scoped tests support them.
Do not fabricate approvals, deployments, test outputs, legal citations, file paths, line numbers, production settings, or evidence of delivered email. Never mark a launch gate passed solely because documentation says "implemented."
